# 文档处理模块说明

对应代码：`app/document_processor.py`

## 为什么需要这一层

模型不能直接高质量地检索一整份 Markdown 文件。我们先把原始文档转成统一的 `DocumentChunk`，后续所有检索方式都使用同一份数据：

```text
原始 Markdown
  -> 清洗
  -> 识别标题和章节
  -> 提取文档元数据
  -> 按段落切 Chunk
  -> 输出 JSONL
```

如果后面回答错误，可以按下面的顺序排查：

1. 原文是否被正确读取；
2. Chunk 是否保留了完整语义；
3. 检索是否找到了正确 Chunk；
4. 模型是否正确使用了检索结果。

## `DocumentChunk` 字段

| 字段 | 用途 |
|---|---|
| `chunk_id` | Chunk 的稳定唯一标识 |
| `source` | 原始文件名 |
| `title` | 文档标题 |
| `document_id` | 制度文档编号 |
| `version` | 文档版本 |
| `effective_date` | 生效日期 |
| `department` | 负责部门 |
| `section` | 所属章节 |
| `text` | 真正参与检索的正文 |
| `start_line` / `end_line` | 方便回到原文定位证据 |

## 为什么元数据不放进正文

例如 `版本：v1.0`、`负责部门：财务部` 是文档属性，不是制度内容。如果把它们混进正文，向量检索可能因为“财务部”这个词召回错误片段。它们应该作为结构化字段保留，后面可用于过滤和引用。

## 为什么 `chunk_id` 要稳定

代码用以下内容计算哈希：

```text
来源文件 + 章节 + 行号 + Chunk 文本
```

相同输入会得到相同 ID。这样重复执行建库不会产生随机 ID，也方便后续做增量更新、去重和评测对齐。

## 为什么要保留重叠文本

如果一个完整规则刚好跨越两个 Chunk 边界，检索其中一个 Chunk 时可能缺少条件。切分长段落时保留少量重叠，可以降低这种边界损失。重叠不是越大越好，过大会增加重复内容、向量数量和上下文成本。

## 当前版本的限制

- 当前只读取 Markdown；
- 当前按标题和段落切分；
- 当前使用字符数近似长度，不是 Token 数；
- 尚未处理 PDF 表格、扫描件和复杂 HTML；
- 尚未做 Embedding 和检索。

这些限制是有意保留的。先把简单输入链路跑通，再逐步加入 PDF、Token 计数和复杂解析，便于定位问题。
